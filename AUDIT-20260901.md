## P1 — Breekt updates of run-tijd

### 1. `vscode-extensions` heeft geen subprocess-timeout

- `main.zig:1720` — `subprocess.run(["code","--update-extensions"], capture_output=True)` zonder `timeout=`.
- Gevolg in log: `done vscode-extensions TimedOut (1800.1s)`, daarna een retry die in **3.1s** "no output" gaf.
- De watchdog vangt het pas op de globale `task_timeout_sec = 1800` (`main.zig:329`). Dat is de default voor *alle* taken en veel te ruim voor een extensie-check.
- Fix:
  - `subprocess.run(..., timeout=300)` plus `except subprocess.TimeoutExpired: print("timed out"); sys.exit(1)`.
  - Geef de task een eigen `.timeout_sec = 300` via `Opts` (veld bestaat al, `main.zig:2441`).
  - Bonus: `"no output"` levert nu status `Succeeded` zonder enig bewijs dat er iets gebeurd is. Laat dat `Skipped` worden.

### 2. Versievergelijking strip-t alle niet-cijfers

- `main.zig:1069-1079`, `Test-UpToDate`:
  - `[version]::TryParse` faalt op een kaal buildnummer, daarna fallback `($l -replace '\D','')` met `[int64]`-vergelijk.
  - Log: `ggml-org/llama.cpp local=10649 latest=v0.3.0` → `10649 >= 30` → **"up to date"**. llama.cpp wordt via deze task dus nooit geüpdatet.
  - Zelfde klasse fout binnen semver: `1.2.10` → `1210` telt hoger dan `1.3.0` → `130`.
- Tweede oorzaak: `releases/latest` is de verkeerde bron voor repos die per build taggen (`b10711`); GitHub geeft daar een oude "latest release" terug.
- Fix:
  - Voeg `version_scheme` toe aan `GithubTool` (`semver` | `build` | `date`) en vergelijk per schema. Haal de digit-strip fallback weg; bij onbekend schema niet up-to-date aannemen.
  - Voor llama.cpp: `/releases?per_page=20`, filter `tag_name -match '^b\d+$'`, neem de hoogste.

### 3. Retry herhaalt deterministische fouten

- `main.zig:3409-3416` — de retry-lus kijkt alleen naar `status == Failed || TimedOut`, nooit naar de reden.
- Log-bewijs, 3x identiek per task:
  - `hermes` → `RuntimeError: SCM service QingpingLogger has indeterminate status: paused`.
  - `wsl-distros` → `File has unexpected size (21402149 != 21402655)` op de kali mirror.
- Kosten: 3 pogingen plus 6s/12s/24s wachten x 2 taken = ~2 min verspilling en veel logruis.
- Fix:
  - Veld `Task.no_retry_patterns: []const []const u8`; match na een fail tegen de output-tail en ga direct naar `Failed`.
  - Generiek alternatief: identieke `output_tail` twee runs op rij ⇒ stop met retryen.
  - Losse actie buiten de code: de service `QingpingLogger` staat op `paused`. Hervat of verwijder 'm, anders blijft `hermes` elke run rood.

## P2 — Races en correctheid

### 4. `uv-tools` race met de `uv` task

- Log: `uv-tools spawn failed: FileNotFound` (2x), daarna succes.
- Twee samenwerkende oorzaken:
  - Geen `depends_on` van `uv-tools` op `uv`, terwijl `uv` in dezelfde run `uv.exe` vervangt (winget installeerde 0.12.8).
  - De PATH-cache (`buildPathIndex` / `resolveCommandPath`, `main.zig:2940-3018`) resolve't paden één keer bij startup; een binary die tijdens de run verplaatst wordt, blijft naar het oude pad wijzen.
- Fix:
  - `.depends_on = &.{"uv"}` op `uv-tools`; het mechanisme werkt al (`dependenciesMet`, `main.zig:3401`).
  - Bij `error.FileNotFound` op spawn eerst `resolveUncached` opnieuw draaien vóór de retry.

### 5. De "notify"-task muteert het systeem

- `github_notify_body`, `main.zig:1156-1210` — bij een match draait hij zelf `npm install -g $pkg@latest` en `winget upgrade --id $id`.
- Matching is substring, niet exact: `$wl.Contains($name)` en `$npm.Contains("/$name@")`. Repo-namen als `fd` of `codex` matchen veel te breed; de gekozen `$id` komt uit een losse regex over `winget upgrade`-output.
- Log: heeft daadwerkelijk `@google/gemini-cli` geïnstalleerd, met npm-warns over `@github/keytar` install-scripts.
- Fix:
  - Expliciete `repo -> package-id` map in `update-config.json`, geen fuzzy match.
  - Default alleen rapporteren; installeren achter een `--notify-apply` flag.

### 6. GitHub-release updater kilt draaiende apps zonder vragen

- `main.zig:1097-1101` — `Get-Process | Where Path.StartsWith($dir) | Stop-Process -Force`, onvoorwaardelijk vóór elke extract.
- Raakt o.a. `D:\Games\Ikemen_nightly` en de OpenRGB-installdir; een draaiende sessie wordt hard afgebroken.
- Fix: eerst `Expand-Archive` proberen en alleen bij een lock-fout processen stoppen, achter een `--force-kill` opt-in.

### 7. Geen integriteitscheck op downloads

- Assets gaan via `Invoke-WebRequest` direct naar `Expand-Archive -Force` in de installdir: geen hash, geen handtekening.
- Fix: vergelijk met `$dl.digest` uit de GitHub asset-API; ontbreekt die, log expliciet "unverified".

## Architectuur

- **Alle ~40 update-scripts zijn PowerShell/Python heredocs in Zig string-literals.** Geen syntax-check, geen linter, geen unit-test; een typo in PowerShell blijkt pas tijdens een run van een half uur.
  → Verplaats naar `scripts/*.ps1` en `scripts/*.py`, laad met `@embedFile`, zet PSScriptAnalyzer + ruff in CI. Grootste enkelvoudige verbetering.
- **Vier implementaties van dezelfde taakdefinities**: `updatescript.ps1` (216 KB), `rewrites/zig` (4182 regels), `rewrites/rust` (4273 regels), `rewrites/go` (~2.1k regels, duidelijk achter). Ze lopen uit elkaar; bugfixes landen maar in één.
  → Kies zig als canoniek, archiveer rust/go/ps1 onder `legacy/`, documenteer dat in `README.md`.
- **Tests dekken alleen pure helpers** (`classifyStatus`, string-utils). Geen enkele test op script-generatie.
  → Snelle winst: golden-tests op de gegenereerde argv per task (`buildTasks` → `shellJoin`), zodat een gebroken template bij `zig build test` valt.
- `main.zig` is één bestand van 4182 regels. Split minimaal in `cli.zig`, `tasks.zig`, `runner.zig`, `report.zig`.
